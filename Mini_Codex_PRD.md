# Mini Codex --- Product Requirements Document (PRD)

**Document status:** Initial product specification\
**Version:** 1.0\
**Product type:** Local-first, terminal-based AI coding agent\
**Primary language:** Python\
**LLM provider:** Groq\
**Target user:** Developer working on a local codebase\
**MVP interface:** Command-line interface (CLI)

------------------------------------------------------------------------

## 1. Product Overview

Mini Codex is a small, local-first AI coding agent inspired by tools
such as Codex and Claude Code. It uses a Groq-hosted large language
model (LLM) and a controlled set of Python tools to inspect a codebase,
investigate a reported issue, propose a minimal code change, request
human approval, apply the approved change, and run tests.

The product is an agent, not merely a chatbot. The LLM repeatedly
chooses a tool, receives the tool result, and decides what to do next.
Python code---not the LLM---executes tools, validates arguments,
enforces permissions, applies edits, and controls testing.

### 1.1 Product goal

Build a working, testable MVP that can fix deliberately introduced bugs
in a small Python project while preserving human control over every
source-code modification.

### 1.2 Non-goals for the MVP

The first version will not: - Reproduce every capability of Codex or
Claude Code. - Autonomously edit files without explicit approval. -
Execute arbitrary shell commands generated by the LLM. - Support a
graphical/web interface. - Support multi-agent collaboration. - Make
network requests to external services other than the configured LLM
provider. - Guarantee that every proposed fix is correct. -
Automatically commit, push, reset, or otherwise manipulate Git
history. - Index or transmit secrets, `.env` files, credentials, or
private keys to the LLM.

------------------------------------------------------------------------

## 2. Problem Statement

When a developer reports a bug, they must manually locate relevant
files, trace the faulty logic, edit code, and run tests. A small coding
agent can assist with this workflow, but unrestricted file access and
automatic execution create unnecessary risk.

Mini Codex aims to automate investigation and routine repair while
keeping the developer in control. The agent must provide evidence for
its diagnosis, show an exact diff before changing source code, and
verify the result with tests.

------------------------------------------------------------------------

## 3. Target User and Main Use Case

### Primary user

A developer working in a local repository who wants help finding and
fixing a bug without handing unrestricted control of the repository to
an AI model.

### Main user story

> As a developer, I want to describe a bug in natural language so that
> the agent can inspect the relevant code, propose a minimal fix, show
> me the exact changes, wait for my approval, apply the approved patch,
> and run tests to report whether the fix worked.

### Example task

User: "The discount calculation is incorrect. Find the issue and fix
it."

Expected agent behavior: 1. Search the codebase for relevant files and
terms. 2. Search inside candidate files for relevant functions and
symbols. 3. Read the relevant code with line numbers and enough
surrounding context. 4. Form a diagnosis based on source evidence. 5.
Prepare a minimal patch without changing the source file. 6. Show the
diff, explanation, and affected file to the user. 7. Ask for explicit
approval. 8. If approved, validate and apply the patch. 9. Run the
permitted test command. 10. Give a truthful summary of the change and
test results.

------------------------------------------------------------------------

## 4. Product Principles

1.  **Human control:** No source edit is applied without explicit
    approval.
2.  **Minimal change:** Prefer the smallest patch that addresses the
    diagnosed problem.
3.  **Evidence before editing:** Inspect source code before proposing a
    fix.
4.  **Tool-driven behavior:** The LLM selects from registered tools;
    Python executes them.
5.  **Safe defaults:** Reject ambiguous edits, unsafe paths, and
    unapproved commands.
6.  **Verifiable results:** Report actual test output and exit status;
    never claim success without evidence.
7.  **Bounded autonomy:** Apply iteration limits, timeouts, output
    limits, and cancellation.
8.  **Traceability:** Keep a task-local history of tool calls, results,
    proposed diffs, approval decisions, and tests.
9.  **No secret exposure:** Never index or send secret files to the LLM.
10. **Recoverability:** Preserve enough information to recover from an
    interrupted or failed edit.

## 6. Agent Workflow

The agent runs as a bounded loop:

1.  Read the user's task and initialize task state.
2.  Send the task, relevant history, and available tool schemas to Groq.
3.  Receive a final response or one or more tool calls.
4.  Validate each tool name and its arguments.
5.  Execute the approved tool implementation in Python.
6.  Add the structured result to the conversation.
7.  Continue the loop until the model finishes, the user cancels, a
    fatal error occurs, a patch is rejected, or the iteration limit is
    reached.
8.  Return a final report.

The LLM may repeat searching and reading when the evidence is
insufficient. It should not be forced to edit after a fixed number of
searches. The loop must nevertheless have a configurable maximum number
of model turns and tool calls.

### 6.1 State machine

The task state should use explicit states similar to:

-   `IDLE`
-   `INVESTIGATING`
-   `PATCH_PROPOSED`
-   `AWAITING_APPROVAL`
-   `PATCH_APPLIED`
-   `TESTING`
-   `COMPLETED`
-   `REJECTED`
-   `FAILED`
-   `CANCELLED`

Valid transitions must be enforced in Python. For example, a patch
cannot move from `PATCH_PROPOSED` to `PATCH_APPLIED` unless the user
explicitly approves it and patch validation succeeds.

### 6.2 Approval and rejection behavior

**Approval (`y` / `yes`):** - Revalidate the project-relative path. -
Confirm that the original content still matches the content used to
prepare the patch. - Verify the patch is the pending patch the user
saw. - Create a recoverable backup or equivalent local recovery point. -
Apply the smallest patch possible. - Record the result and proceed to
testing.

**Rejection (`n` / `no`, or empty input):** - Treat rejection as the
default. - Discard the pending patch. - Do not change the source file. -
Do not run tests as though the patch had been applied. - Report that the
proposed change was rejected. - Do not silently create and apply another
patch in the same approval step.

**Unexpected input:** - Ask again for a valid answer or cancel safely. -
Never interpret an unclear answer as approval.

## 7. Tool Specifications

The product has six logical tools. The LLM chooses tools, but Python
owns their implementation and safety checks.

### Tool 1: `search_codebase`

**Purpose:** Find files and symbols relevant to the task.

**Inputs:** - `query`: required string describing a term, symbol, or
search phrase. - `extensions`: optional list of allowed file
extensions. - `max_results`: optional bounded result limit.

**Outputs:** - Relative file paths. - Matching terms or brief match
context where appropriate. - Number of matches and any truncation
indicator.

**Requirements:** - Search only within the selected project root. -
Ignore `.git`, `.venv`, `venv`, `node_modules`, build output, caches,
binary files, and configured excluded directories by default. - Exclude
`.env`, credential files, private keys, and likely secret files. - Limit
file size, result count, and output size. - Do not follow symlinks
outside the project root. - Return a useful "no matches found" result
rather than crashing.

### Tool 2: `search_in_file`

**Purpose:** Find a term or pattern inside a specific file.

**Inputs:** - `path`: project-relative file path. - `query`: search term
or supported pattern. - `context_lines`: optional number of surrounding
lines.

**Outputs:** - Relative file path. - Matching line numbers. - Matching
text and bounded surrounding context. - Truncation or error information
when relevant.

**Requirements:** - Validate the path independently of the LLM. - Use a
documented search mode. Literal text search should be the default; regex
must be explicitly supported and safely bounded if implemented. - Never
read excluded secret files. - Handle missing files, unreadable files,
invalid patterns, and binary files safely.

### Tool 3: `read_file`

**Purpose:** Read the relevant portion of a source file.

**Inputs:** - `path`: project-relative file path. - `start_line`:
positive line number. - `end_line`: line number greater than or equal to
`start_line`.

**Outputs:** - Relative path. - Exact source lines with line numbers. -
Actual line range returned. - Truncation information, if applicable.

**Requirements:** - Validate path and file type. - Enforce maximum
line-range and output-size limits. - Preserve source text accurately. -
Return useful errors for invalid ranges or missing files. - Allow the
agent to make another read request if it needs more context.

### Tool 4: `propose_edit`

**Purpose:** Prepare a minimal patch without modifying the source file.

**Inputs:** - `path`: project-relative path. - `old_text`: exact source
text to replace. - `new_text`: replacement source text. - `reason`:
concise explanation of why the edit addresses the diagnosed issue.

**Outputs:** - Unique pending patch ID. - File path. - Unified diff. -
Brief change summary. - Validation status.

**Requirements:** - Do not write to the original source file. - Require
an exact match for `old_text`. - Reject a missing match. - Reject
multiple matches unless an explicit, unambiguous replacement strategy is
supported. - Refuse an empty `old_text` for normal replacement
operations. - Record a hash or equivalent fingerprint of the source
version used to prepare the patch. - Limit patch size. - Keep the
pending patch in task state; do not trust the LLM to reconstruct
approval status. - Do not allow edits to excluded, protected, or
out-of-root files. - Treat generated diff text as data, not as
executable commands.

### Tool 5: `request_approval_and_apply`

**Purpose:** Present the exact proposed diff and apply it only after
human approval.

**Inputs:** - `patch_id`: ID of the pending patch.

**Terminal display must include:** - File path. - Explanation of the
problem. - Explanation of the proposed fix. - Unified diff. - Clear
approval prompt, such as `Apply this change? [y/N]`.

**Outputs:** - Approval decision. - Whether the patch was applied. -
Changed file path and summary. - Validation or application error, if
any.

**Requirements:** - Approval is collected by Python from the actual
terminal user. - Only the pending patch identified by `patch_id` may be
applied. - Empty input and invalid input must not result in approval. -
Revalidate the path, source fingerprint, and exact original content
before writing. - Refuse stale patches if the file changed after
inspection. - Preserve file encoding and line endings where feasible. -
Use an atomic-write strategy where practical and retain a recovery
copy. - Do not overwrite unrelated user changes. - If application fails,
recover safely and report the failure. - A rejection must leave the
source file unchanged. - Do not run tests after a rejected patch.

### Tool 6: `run_tests`

**Purpose:** Test an approved edit.

**Inputs:** - `test_target`: optional approved test file or target. -
`test_profile`: a predefined, trusted test configuration.

**Outputs:** - Command/profile used. - Exit code. - Bounded stdout and
stderr. - Duration. - Pass/fail/timeout status.

**Requirements:** - Start with `pytest` for the Python MVP. - Do not
accept arbitrary shell commands from the LLM. - Use a predefined command
and argument allowlist. - Validate test targets against the project
root. - Set a configurable timeout. - Limit captured output. - Run tests
in a controlled environment where possible. - Do not claim tests passed
when the runner timed out, could not start, or returned a nonzero exit
code. - Return structured results to the LLM for final interpretation. -
A failed test may lead to further investigation and a new proposed
patch, which requires fresh human approval.

## 8. LLM Integration with Groq

### 8.1 Configuration

The API key and model configuration must be read from environment
variables.

Example `.env` configuration:

``` dotenv
GROQ_API_KEY=replace_with_your_key
GROQ_MODEL=your_supported_tool_calling_model
MAX_AGENT_TURNS=20
MAX_TOOL_CALLS=40
TOOL_TIMEOUT_SECONDS=30
TEST_TIMEOUT_SECONDS=120
```

The model name above is a placeholder. Use a Groq model that is
currently available to the account and supports the required
tool-calling behavior.

### 8.2 LLM responsibilities

The LLM is responsible for: - Interpreting the user's issue. - Selecting
the next registered tool. - Supplying arguments that match the tool
schema. - Interpreting search results and source code. - Explaining the
suspected root cause. - Preparing a minimal proposed edit. -
Interpreting test results. - Producing the final report.

### 8.3 Python runtime responsibilities

Python is responsible for: - Loading configuration. - Sending requests
to Groq. - Providing registered tool schemas. - Validating tool calls
and arguments. - Executing tool functions. - Enforcing path, file,
patch, and command restrictions. - Tracking task state and approval. -
Applying patches only after approval. - Enforcing timeouts and iteration
limits. - Capturing errors and test results. - Maintaining an auditable
task history.

### 8.4 Tool-calling loop requirements

-   Send tool schemas in the format supported by the selected Groq
    API/model.
-   Handle responses containing tool calls, final text, malformed
    arguments, and provider errors.
-   Return tool results using the required tool-call identifiers and
    response format.
-   Never dispatch a tool that is not registered.
-   Validate arguments using explicit schemas or equivalent validation.
-   Do not use `eval`, `exec`, or dynamic imports to execute model
    output.
-   Retry transient provider failures only a bounded number of times.
-   Do not retry non-recoverable errors indefinitely.
-   Keep prompts and tool output within configured context/output
    budgets.
-   Treat repository content as untrusted input. Code comments, README
    files, or test fixtures must not override the agent's safety rules.

## 11. Safety and Security Requirements

### 11.1 Filesystem security

-   Require a valid project root selected by the user.
-   Resolve paths before access and reject traversal such as
    `../../secret.txt`.
-   Ensure resolved paths remain inside the project root.
-   Reject symlinks that escape the root.
-   Use a configurable exclusion list.
-   Exclude `.env`, private keys, credentials, and common secret/config
    files by default.
-   Do not follow ignored dependency and build directories.
-   Never treat the LLM's path validation as sufficient; validate in
    Python.

### 11.2 Editing safety

-   No direct source edits during investigation or patch preparation.
-   Require an exact, unambiguous original-text match.
-   Verify source fingerprints before applying a patch.
-   Show the actual diff before asking for approval.
-   Treat missing approval as rejection.
-   Require new approval for every new patch.
-   Never silently overwrite a file that changed concurrently.
-   Do not use broad file rewrites when a narrow patch is possible.
-   Preserve unrelated user changes.
-   Record what was changed and whether recovery succeeded.

### 11.3 Command execution safety

-   Do not expose an unrestricted shell tool to the LLM.
-   Use a predefined test profile, executable, and argument allowlist.
-   Do not interpolate LLM output into a shell command.
-   Apply timeouts and output limits.
-   Explain that running repository tests executes project code.
-   Use an isolated environment where feasible, especially for untrusted
    repositories.

### 11.4 Secret handling

-   Keep `.env` out of version control.
-   Commit `.env.example` with placeholder values only.
-   Never print the API key.
-   Never include secret file contents in model context or diagnostic
    logs.
-   Avoid logging authorization headers or raw provider request objects
    that may contain secrets.
-   Fail with a clear configuration error if the API key is missing.

### 11.5 Prompt injection

Repository files may contain text that instructs the model to ignore its
rules or expose secrets. The agent must treat such text as untrusted
codebase content. Safety controls must be enforced in the Python
runtime, not merely described in the system prompt.

## 12. Error Handling

The agent must handle these conditions without crashing or making unsafe
changes:

-   Missing or invalid Groq API key.
-   Unsupported model or provider error.
-   Network timeout or rate limit.
-   Malformed LLM response.
-   Unknown tool name.
-   Invalid tool arguments.
-   No search results.
-   Missing or unreadable file.
-   File too large or binary.
-   Out-of-root path.
-   Secret-file access attempt.
-   Missing or ambiguous patch target.
-   Source file changed since inspection.
-   Permission error while applying a patch.
-   Patch application failure.
-   Invalid approval input.
-   User rejection or cancellation.
-   Test failure or timeout.
-   Maximum agent turns/tool calls reached.

Errors returned to the LLM should be structured, concise, and safe. They
must not reveal secrets or full sensitive environment details.

## 13. Testing and Evaluation Plan

Testing is a core product feature, not an optional final step.

### 13.1 Fixture projects

Create a small isolated fixture repository containing independent Python
modules with deliberate bugs. The test suite must encode expected
behavior before the agent is asked to repair them.

#### Fixture A: `buggy_discount.py`

Example bug: a percentage is subtracted as a whole number rather than
converted to a fraction.

Expected behavior: - A price of 100 with a 20% discount results in 80. -
A price of 50 with a 10% discount results in 45. - Boundary and
invalid-input behavior is defined by the fixture's tests.

#### Fixture B: `buggy_cart.py`

Example bug: iteration bounds omit the final cart item.

Expected behavior: - Every item contributes to the total. - Empty and
single-item carts behave according to the defined test contract.

#### Fixture C: `buggy_pricing.py`

Example bug: an incorrect comparison operator at a price boundary.

Expected behavior: - Boundary cases follow explicit tests. - The fix
must not alter unrelated pricing behavior.

The fixture tests must be independent of the agent implementation. Avoid
tests that simply repeat the buggy implementation's logic.

### 13.2 Unit tests

Test each tool in isolation: - Search includes relevant files and
excludes configured paths. - Search returns line numbers and respects
result limits. - File reading returns correct lines and handles invalid
ranges. - Patch preparation does not modify the source. - Missing or
ambiguous old text is rejected. - Patch application refuses stale source
fingerprints. - Rejected approval leaves file bytes unchanged. -
Out-of-root paths are rejected. - Test execution respects allowlists and
timeouts.

### 13.3 Integration tests

-   Mock the Groq response and verify the tool-call loop.
-   Verify tool results are returned to the correct tool-call
    identifiers.
-   Verify errors are passed back to the model in the expected format.
-   Verify the agent stops on final output, cancellation, rejection,
    fatal error, and iteration limits.
-   Verify the agent does not apply a patch before approval.
-   Verify the agent runs tests only after successful patch application.

### 13.4 End-to-end scenarios

**Scenario 1 --- Successful repair** 1. Start with a buggy fixture and
failing tests. 2. Give the agent a natural-language task. 3. Verify it
discovers the relevant file without being told the path. 4. Verify it
inspects the function before proposing an edit. 5. Approve the diff. 6.
Verify the source changes only in the intended area. 7. Verify tests run
and the actual results are reported.

**Scenario 2 --- Rejected repair** 1. Start with a buggy fixture. 2. Let
the agent prepare a patch. 3. Reject the patch. 4. Verify the source
file is byte-for-byte unchanged. 5. Verify the rejected patch is not
applied later without fresh approval.

**Scenario 3 --- Incorrect repair** 1. Have the model propose an
intentionally incorrect patch or use a controlled mock. 2. Approve the
patch. 3. Verify tests fail. 4. Verify the agent reports failure rather
than success. 5. If it proposes another fix, verify fresh approval is
required.

**Scenario 4 --- Unsafe path** - Ask the agent to inspect or edit a file
outside the project root. - Verify the tool rejects the request.

**Scenario 5 --- Ambiguous patch** - Create multiple occurrences of the
target text. - Verify the tool refuses the patch unless the target is
made unambiguous.

**Scenario 6 --- Concurrent modification** - Modify a file after patch
preparation but before approval. - Verify the pending patch is rejected
as stale.

**Scenario 7 --- Tool-loop failure** - Simulate invalid tool calls,
provider errors, and a model that never finishes. - Verify bounded
retries and termination.

### 13.5 Evaluation metrics

Record these metrics during testing: - Task completion rate on the known
fixture set. - Correct bug localization rate. - Percentage of patches
accepted by tests. - Rejection integrity rate: rejected patches that
leave files unchanged. - Unauthorized modification count; target is
zero. - Out-of-root access success count; target is zero. - Tool-call
count per task. - End-to-end duration. - Test runner timeout and failure
rate.

A small fixture set is useful for verifying the workflow but is not
sufficient evidence that the agent can reliably repair arbitrary
repositories.

## 15. Setup and Dependencies

Use a supported Python version and pin compatible dependency versions in
the project's package configuration.

Expected dependency categories: - Groq Python SDK for model requests and
tool calling. - `python-dotenv` for local `.env` configuration. - A
schema-validation library such as Pydantic, or equivalent explicit
validation. - `pytest` for automated tests. - A diff utility from the
Python standard library or a small, maintained library.

Keep dependencies minimal. Do not add a framework or database unless a
concrete requirement justifies it.

### Setup expectations

1.  Create and activate a virtual environment.
2.  Install the project and development dependencies.
3.  Copy `.env.example` to `.env`.

## 16. Implementation Phases and Acceptance Gates

### Phase 1 --- Groq foundation and agent loop

Deliver: - Project scaffold. - Environment configuration. - Groq client
wrapper. - Registered tool schemas and dispatcher. - Task state and
bounded loop. - Mock-tool test.

Acceptance gate: - A model tool call is validated, executed, and
returned to the model correctly. - Unknown tools are rejected. - Missing
configuration fails safely. - The loop terminates at its configured
limit.

### Phase 2 --- Codebase exploration

Deliver: - `search_codebase`. - `search_in_file`. - `read_file`. - Path
restrictions, exclusions, and output limits.

Acceptance gate: - The agent can locate and read a deliberately broken
function without being given its path. - Excluded secrets and
out-of-root files are not exposed. - Missing files and empty results are
handled safely.

### Phase 3 --- Patch preparation and human approval

Deliver: - `propose_edit`. - Unified diff generation. -
`request_approval_and_apply`. - Pending patch state, source
fingerprints, and recovery behavior.

Acceptance gate: - Proposed edits do not change the file. - Approval
applies only the displayed patch. - Rejection leaves source bytes
unchanged. - Stale or ambiguous patches are refused.

### Phase 4 --- Test execution and repair feedback

Deliver: - Safe, predefined test runner. - Bounded output and
timeouts. - Structured test results returned to the LLM. - Final
reporting and controlled re-proposal flow.

Acceptance gate: - Tests run only after an approved patch is applied. -
Passing and failing tests are reported correctly. - A follow-up patch
requires a new approval.

### Phase 5 --- End-to-end verification and documentation

Deliver: - Three buggy fixture modules. - Fixture tests and end-to-end
scenarios. - Safety regression tests. - README and usage
documentation. - Final evaluation report.

Acceptance gate: - Successful repair, rejection, failed repair, unsafe
path, ambiguous patch, stale patch, and loop-limit scenarios all behave
as specified. - No unauthorized source modifications occur in the test
suite. - All automated tests pass, except any explicitly documented
environment-dependent tests.

Do not proceed to the next phase until the current phase's acceptance
gate is met.

## 17. Definition of Done

The MVP is complete when all of the following are true:

-   [ ] Groq credentials are loaded from environment configuration and
    are never committed.
-   [ ] The CLI accepts a natural-language coding task.
-   [ ] The LLM chooses among registered tools using supported tool
    calling.
-   [ ] The agent can search the project, search within a file, and read
    a selected line range.
-   [ ] The agent can prepare a targeted patch without changing source
    files.
-   [ ] The CLI displays the exact diff and requires explicit approval.
-   [ ] Approval applies only the validated pending patch.
-   [ ] Rejection leaves source files unchanged.
-   [ ] Stale and ambiguous patches are refused.
-   [ ] The test runner uses a predefined, bounded command.
-   [ ] Actual test results are returned to the LLM and reported
    accurately.
-   [ ] Tool calls, iterations, output, and test duration are bounded.
-   [ ] Filesystem and secret protections have automated tests.
-   [ ] The deliberately buggy fixture suite covers successful and
    unsuccessful repair flows.
-   [ ] The README documents installation, configuration, use, testing,
    and limitations.

## 20. Final Product Summary

Mini Codex is a Groq-powered, Python-based coding agent that
investigates bugs through a bounded tool loop, proposes minimal patches,
waits for human approval, applies only validated changes, and tests the
result using controlled commands.

The core product requirement is not merely that the LLM can generate a
fix. It is that the entire workflow is **traceable, testable, bounded,
and safe by default**.

Implementation should proceed through the five phases in order, with
each phase accepted only after its tests and safety checks pass.
